# Implementation Plan: Real Purchase Data (Release 1, Phase 1)

**Branch**: `zharfa-prd-phase-1` | **Date**: 2026-11-16 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-real-purchase-data/spec.md` · Phase ref `zharfa-prd.phases.md#1` · Governing PRD `zharfa-prd.md` v3.0 (F1–F4) · Rules `AGENTS.md`

## Summary

Give the Admin a read-only sync of Mabna purchasing data (vendors, products, purchase invoices, purchase returns, lines) into PostgreSQL, give the Manager a purchasing Overview with reconciled figures, and separate production and demo installs so real and synthetic data never mix.

Technical approach (details in [research.md](research.md)):

- **Verify first, configure the rest.** The sync works on a logical purchasing model. Real Mabna table, column and operation-code names live in a **gitignored source map** with a verification status per item. Production uses only `confirmed`/`corrected` items. Unverified or unmapped items make the figures that depend on them show "data unavailable" (R1–R3).
- **Reuse the spec 002 connector as it is.** Keyset-paged, guarded SELECTs through `IMabnaReader`: allowlist, hard exclusions, SELECT-only guard, read-only login check, and rollback-only transactions. No aggregates or joins are added to the connector (R4).
- **Sync engine.** Per-table change strategies (`rowversion`, `modifiedAt`, `idWatermark`, `full`). Header tables are read in full (`idWatermark`) or by change marker plus a key-only pass (`rowversion`, `modifiedAt`), so deletions and cancellations reach the copy on every run; no lookback window remains (R5, Phase 13). A weekly full run stays scheduled as a full load with the same result. All data changes of a run go into **one PostgreSQL transaction**. Job and log rows go through a separate connection, a partial unique index plus an advisory lock allow only one running job, and a `BackgroundService` scheduler runs at 02:00 Asia/Tehran (R5–R7).
- **Storage.** A new `mabna` schema holds the synced copy. The reserved `sync_job`/`sync_log`/`source_record` tables are extended, and `install_setting` and `reconciliation_run` are new (R8, [data-model.md](data-model.md)).
- **One definition per metric.** Each metric is defined once, as a PostgreSQL function in `mabna`, and documented in `docs/metrics/purchasing.md`. Net = invoices − returns, excluding VAT, by document date. The discount basis is configurable: `line` until the on-site check, then Mabna's own basis (R9).
- **Reconciliation.** A developer-run CLI mode of the API compares the Overview's SQL totals with an independent C# recomputation from fresh guarded source reads, metric by metric, with exact decimals. It logs to `reconciliation_run` and returns exit code 1 on a mismatch. On-site it is cross-checked with the gitignored control-total script (R11).
- **Data mode.** `Zharfa__DataMode` (`production`|`demo`) is required and fixed per database. Production never applies `db/seed/*`, bootstraps its accounts from the environment, and gets 404 from a server-side `[DemoOnly]` filter on Demo 1 and AI endpoints. Labels are driven by `GET /api/system/status` (R12).
- **Frontend.** New Overview (purchasing) page, Data sync page, last-sync indicator and mode badge. No new npm dependencies: an inline SVG trend chart and a view switcher instead of a router (R13, R14).

## Technical Context

**Language/Version**: C# on .NET 10 (`net10.0`), TypeScript 7 / React 19, SQL (PostgreSQL 18; T-SQL SELECTs generated by the connector only)

**Primary Dependencies**: ASP.NET Core Web API, Npgsql + EF Core (existing), Microsoft.Data.SqlClient 7.1.2 (existing, spec 002 connector), Vite 8 + Tailwind 4 (existing). **No new packages** (backend, tests or frontend).

**Storage**: PostgreSQL 18. New schema `mabna`; migrations `0005_purchasing_sync.sql`, `0006_purchasing_kpis.sql`. Source is Mabna SQL Server (read-only): `deploy/mabna-sim/` in development, live `TotalSystem` on-site only.

**Testing**: xunit 2.9 (`backend/Zharfa.Api.Tests`): pure logic only, no DB or network (validation rule). End-to-end flows run with Docker Compose and the simulator per [quickstart.md](quickstart.md). Frontend is checked by `tsc -b` + Vite build and the quickstart UI steps.

**Target Platform**: Linux containers with Docker Compose on the company LAN server. The WebView2 desktop shell is unchanged.

**Project Type**: Web application (ASP.NET Core API + React SPA) plus a CLI mode of the same API for reconciliation.

**Performance Goals**: Overview API p95 < 2 s with three years of data (SC-005); first screen < 3 s on the LAN; a full sync of about 416k rows in the largest table completes off-hours, with each source command under its 60 s timeout.

**Constraints**: Mabna is read-only (login first, guard and allowlist second). Nothing from Mabna is committed (real names stay in gitignored config). `HOST_ID()`-filtered report views are never read live. Secrets stay in env/Docker secrets only. Persian RTL, Jalali, Persian digits, Rial («ریال»). All KPIs are computed server-side. Real and demo data never mix.

**Scale/Scope**: 20 concurrent users. Five logical source tables. Four new API endpoints plus one changed one. Two new SPA pages. One CLI command.

**Unknowns**: None open for planning. The mapping of purchasing source tables and columns and the discount basis remain **on-site verification items**. The design handles them as configuration with enforced statuses (R2), so they do not block the plan. The remaining owner decisions are written down as assumptions in research R16.

## Implementation order (for /speckit.tasks)

Dependency order, aligned with the spec priorities:

1. **Foundation**: data mode (required setting, `install_setting`, seed gating, bootstrap accounts, `[DemoOnly]`, `/api/system/status`), migrations `0005`, source-map model and validator with unit tests, and guard test extensions (US3, US6).
2. **Source verification tooling**: onsite checklist section 7, `source-verification.md` skeleton, simulator purchasing roots and scenario, example map (US1). The on-site visit itself can happen in parallel with steps 3–5.
3. **Sync**: pager, date parser, normalization, planner, runner (single transaction), coordinator, scheduler, admin endpoints, Data sync page (US2).
4. **Metrics**: migration `0006`, `docs/metrics/purchasing.md`, Overview service, endpoint and page, availability rules (US5).
5. **Reconciliation**: `SourceTotalsCalculator`, comparator, CLI, logging (US4).
6. **Docs and deploy**: compose and env changes, READMEs, CHANGELOG. Then run quickstart Flows 1–10 on the simulator. Flow 11 runs on-site before sign-off.

## Risks

| Risk | Mitigation |
|---|---|
| Real purchasing structure differs from the simulator candidates (PRD R1) | Map-driven design. The on-site corrections are config changes followed by a rerun of Flow 7 and Flow 11 |
| No reliable change marker in Mabna | Header tables read in full (`idWatermark`) or with a key-only pass for deletions (`rowversion`, `modifiedAt`), and a fingerprint equivalence check (Flow 6) |
| Discount basis differs from line-level | `Purchasing__DiscountBasis` plus stored raw components. Switching needs no resync |
| A worktree lacks the gitignored simulator files | Quickstart §0 copies `deploy/mabna-sim/generated/` from the main checkout. Unit tests use the committed example map |
| Existing demo installs break on the new required setting | `deploy/.env.example` and the README call it out. The startup error says exactly which key to set |

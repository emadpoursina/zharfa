# Mabna simulator (offline development)

A local SQL Server 2019 container with a database named `TotalSystem` that has
the captured Mabna **schema** and **synthetic demonstration data**. It exists so
the accounting connector (spec 002) can be built and tested offline. It never
connects to any company server.

- **All data is synthetic.** The seed is generated by `gen_seed.py` from a fixed
  random seed. No real row is read, stored or embedded anywhere.
- **FR-02:** anything containing real table or column names lives only in
  `deploy/mabna-sim/generated/` (gitignored). Only generic tooling is tracked.

## Prerequisites

- Docker Desktop. On Apple Silicon enable *Settings > General > Use Rosetta for
  x86_64/amd64 emulation* and give the VM >= 4 GB RAM (the image is x86-64
  only; Rosetta is not officially supported by Microsoft).
- Fallback if 2019 misbehaves: switch both images in
  `deploy/docker-compose.mabna-sim.yml` to `mssql/server:2022-latest` and set
  compatibility level 150 (already done by `generated/00-database.sql`).
- In `deploy/.env` set `MABNA_SIM_SA_PASSWORD` and `MABNA_SIM_RO_PASSWORD`
  (see `deploy/.env.example`; SQL Server complexity rules apply).

## Start / stop / reset

```bash
docker compose -f deploy/docker-compose.mabna-sim.yml up -d       # start + init (first run builds the DB)
docker compose -f deploy/docker-compose.mabna-sim.yml logs mabna-sim-init
docker compose -f deploy/docker-compose.mabna-sim.yml down        # stop, keep data
docker compose -f deploy/docker-compose.mabna-sim.yml down -v     # reset: delete the volume
```

Listens on `127.0.0.1:14330` (`MABNA_SIM_PORT`). Connection string for the
connector: `Server=127.0.0.1,14330;Database=TotalSystem;User Id=zharfa_ro;Password=...;TrustServerCertificate=True`.

The one-shot `mabna-sim-init` container runs `generated/*.sql` and `init/*.sql`
merged in filename order: `00-database`, `01-schema`, `01a-stubs` (only if any), `01b-sim-stubs` (only if any),
`02a-lookups`, `02b-seed`, `03-objects` (functions + views), `04-reports` (report procedures and their runs, only if any)
(all generated), `90-readonly-login` (tracked). Hand-written inputs of the generator live in the gitignored
`generated/src/` (a subdirectory, so the init container does not run them). If `TotalSystem` already exists only `9*` files
are re-run, so `up` is idempotent; use `down -v` to rebuild.

## Read-only login

`init/90-readonly-login.sql` creates `zharfa_ro`: member of `db_datareader`,
with `DENY INSERT, UPDATE, DELETE, ALTER, EXECUTE` (plus CREATE TABLE/VIEW/
PROCEDURE), matching production rights (FR-03). Run the connector as
`zharfa_ro`, never as `sa`.

## Regenerate from a real schema capture

1. On-site run `scratch/mabna-schema-capture.sql` (sqlcmd, `-s"|" -W`), copy the
   output text file to the dev machine.
2. `python3 deploy/mabna-sim/gen_schema.py path/to/capture.txt` writes into
   `generated/`: `00-database.sql` (collation, compat level, recovery, snapshot
   isolation as captured), `01-schema.sql` (tables, column collations, identity,
   defaults, nullability, PKs, indexes, FKs between captured tables),
   `01a-stubs.sql` (minimal stub tables, key columns only and typed from the
   referencing columns, for FK targets outside the capture; FKs to
   `scu*`/`msg*`/user/rights tables are dropped; `--outside-fk drop` drops all
   of them) and `03-views.sql` (only views whose referenced objects are all
   captured; the others are listed as comments). Both the plain and the
   `===== result set N =====` capture formats are accepted.
3. `python3 deploy/mabna-sim/gen_seed.py --capture path/to/capture.txt [--map deploy/mabna-sim/generated/map.json]`
   writes `generated/02-seed.sql` for every created table: captured row count
   x 1% (clamped to 5..2000 rows), FK order, identity, unique keys. The
   optional gitignored `map.json` overrides single columns (`choices`, `cycle`,
   `null_rate`) and row counts; see `gen_seed.py`. Text in `varchar` columns is
   folded to what CP1256 can hold (Persian yeh becomes Arabic yeh, Persian
   digits ASCII); `nvarchar` keeps full Persian.
### Full capture: dependency closure (recommended)

With the full on-site captures (`schema-capture-full.txt`, `definitions-full.sql`,
`lookups.txt`, `row-counts-full.txt`; first capture kept as `--base-capture`):

```bash
D=scratch/mabna-capture-output
python3 deploy/mabna-sim/gen_schema.py $D/schema-capture-full.txt \
  --definitions $D/definitions-full.sql --base-capture $D/schema-capture.txt \
  --lookups $D/lookups.txt --row-counts $D/row-counts-full.txt      # [--roots a,b,c]
python3 deploy/mabna-sim/check_order.py                              # static order/FK checks (no SQL engine)
python3 deploy/mabna-sim/gen_seed.py --capture $D/schema-capture-full.txt \
  --selection deploy/mabna-sim/generated/selection.json --row-counts $D/row-counts-full.txt \
  --lookups $D/lookups.txt [--scenario deploy/mabna-sim/generated/scenario.py] \
  [--map deploy/mabna-sim/generated/map.json]
```

`gen_schema.py` tokenizes the view/function definitions (comments, strings and
brackets handled), follows references transitively from the root views
(default: the views of `--base-capture`), and keeps only real captured objects.
It creates: the base tables, the lookup tables, every referenced table, the FK
parents of all of those (transitively), then functions and views in dependency
order (`03-objects.sql`). Objects with an unreadable (encrypted/NULL)
definition, a reference to a `scu*`/`msg*`/user/rights table, a cross-database
reference, or a dependency on such an object are blocked and reported, never
created. Stored procedures and triggers are never created. `selection.json`
lists what was kept (gen_seed uses it). `02a-lookups.sql` loads the code/label
tables with their real codes (reference data, not business rows) before the
seed. Nothing here needs, or may start, a download or a container; run
`check_order.py` before any load test.

`gen_seed.py --lookups` keeps the lookup tables out of the seed (02a loads them)
but feeds their real codes to every FK column. Without `--scenario` every other
table is filled generically (about 1% of its real row count, 5..2000 rows).

`--scenario FILE` points at a **gitignored** python file (it names real tables and
columns, so it lives in `generated/`, FR-02) that defines `TABLES` (tables it
builds), optional `ROW_COUNTS` and `build_all(ctx)`. `ctx` gives `rng` (fixed
seed), `rows(name)` / `cols(name)` of the tables generated so far (lookups and
generic parents), and Jalali helpers `j2g`, `g2j`, `jadd`. `build_all` returns
`{table: [partial row dicts]}`; seedgen fills every other column (FK parent,
default, NULL or a typed value). Tables that are FK children of scenario tables
are generated after it. This is how the demo company is made internally
consistent (customers, invoices with items, cancelled invoices, returns, opening
invoices, receipts with allocations, cheques with a state history, bounced
cheques, fiscal-year membership; the report scratch tables are filled by the
captured procedures, see below). Mind the letters: the seed text uses Arabic ي
and Persian ک only; Arabic ك appears only in cheque descriptions, as in the real
data. Free-text columns the scenario fills carry the marker "(داده نمايشي)".

Some captured report views read per-host report scratch tables and filter on
`hostid = HOST_ID()`, the client process id. See "Report procedures and HOST_ID()" below:
the simulator fills those tables with the captured filler procedures during init, so
these views return rows too. The other views return rows without any of that.
The lookup load runs with constraints unchecked, so a few FKs show as "not
trusted" in `sys.foreign_keys`; they are valid.

4. (Legacy path.) `docker compose -f deploy/docker-compose.mabna-sim.yml down -v && ... up -d`.

## Report procedures and HOST_ID()

The captured report views read per-host scratch tables that only the captured *filler*
stored procedures write (`DELETE` + `INSERT ... SELECT`, keyed by `hostid`). Those procedures
run **only inside the simulator, during init** (`04-reports.sql`, as `sa`). **Zharfa must never
run them against live Mabna: they write.** The connector's SELECT-only guard rejects
`EXEC`/`INSERT`/`DELETE`, the live login has no write rights, and the simulator's `zharfa_ro`
is denied `EXECUTE`, `INSERT`, `UPDATE`, `DELETE` (checked after every rebuild).

Generate (extra flags of `gen_schema.py`, all optional, all inputs gitignored):

```bash
python3 deploy/mabna-sim/gen_schema.py ... \
  --proc-roots procA,procB,... \                  # procedures to add, with their dependency closure
  --sim-stubs deploy/mabna-sim/generated/src/sim-stubs.sql \
  --report-calls deploy/mabna-sim/generated/src/report-calls.sql \
  --sim-host-id 1
```

* `depclosure.py` now also follows stored procedures (`EXEC`, `DELETE`, nested procedures) so
  the closure pulls in every table, view, function and nested procedure they use; new tables
  are seeded like any other (the scenario adds fiscal-year membership, a current-date constant
  and a configuration row; the scratch tables themselves are **not** seeded).
* `--sim-stubs`: simulator-only stand-ins for objects the capture does not contain
  (security/session objects and a second database the captured code reaches through a
  cross-database name), with synthetic rows. Hand-written, because they name real objects.
  Everything they create counts as known, is written to `01b-sim-stubs.sql` and is listed in
  `generated/sim-changes.txt`. Side effect: the views that read the second database are not
  readable by `zharfa_ro` (no access there); the report views do not.
* `--report-calls`: the `EXEC` statements with synthetic parameters (period, fiscal year,
  center, user) that match the synthetic seed; appended to `04-reports.sql`.
* Captured procedure and view text is created **unchanged**; the only change to captured code
  is the `HOST_ID()` rewrite below (also listed in `sim-changes.txt`).

**HOST_ID().** `HOST_ID()` returns the *client process id* (the TDS login `ClientPID`; it is
the `hostprocess` column of `sys.sysprocesses`), not the session, login or machine. Verified
here with `sqlcmd` and with `Microsoft.Data.SqlClient`: it differs per client process, is
constant within one process, and the connection string's `Workstation ID` (or `sqlcmd -H`)
only changes `HOST_NAME()`, not `HOST_ID()`. Rows a procedure writes during init are
therefore keyed to the init client's process id and a later `zharfa_ro` connection can never
match them. Least-invasive simulator-only fix, done at the end of `04-reports.sql` after
the procedures have run (so they see the real `HOST_ID()` while they execute):

1. the rows written under the init process id are re-keyed to a fixed simulator id
   (`--sim-host-id`, default in our setup `1`);
2. every view/function whose text filters on `HOST_ID()` is `ALTER`ed so that it uses that
   literal instead (`-- SIM CHANGE` comment in each, one line per object in `sim-changes.txt`).

`03-objects.sql` keeps the captured text unchanged.

**Implication for live Mabna.** A read-only client can see rows in those views only if
rows exist for *its own* process id, i.e. only if the same client process previously ran the
writing procedure itself (and a new process, or a restart, gets a new id and sees nothing).
Rows left by other clients are invisible unless some other machine's process id happens to
be identical, which would show unrelated, stale data (ids are not unique across machines and
rows are only cleaned when the same id re-runs). So those views are not a usable read
interface for Zharfa; the connector must read the underlying tables/views directly (the
report views in the allowlist that do not depend on `HOST_ID()`), never the per-host ones.

## Seed edge cases

Legacy/example mode: Jalali dates as text `yyyy/mm/dd` (some with Persian digits)
and numeric `yyyymmdd` side by side; Arabic ي/ك mixed with Persian ی/ک; normal,
cancelled and returned invoices (both sign conventions); uncleared, cleared and
bounced cheques; NULL dates, notes and phones.

Scenario (captured schema): per-table date formats as measured on the real
database (`yyyymmdd`, `yymmdd`, `yy/mm/dd`, `//` for "no date", `Date_Calc`
`yyyymmdd` consistent with them, years 1399 to 1406); sales operation codes 5
(sale), 4 (opening), 33 (return, negative) and 13 (bounced cheque); cancelled
invoices as zeroed headers without items; cheque states R P Q X B H N D T V with
valid transitions, incoming and outgoing (`Input = 0`) instruments; payment
types 1/17/3 (cash-like), 16 and 33 (not cash), 101/102/14/15 and 13.

## Purchasing scenario (spec 003, Release 1)

Synthetic purchasing data for the purchasing feature (quickstart Flows 2, 6 and 7).
Every name the scenario uses is made up or taken from the gitignored candidate map; nothing
here is real. The committed example uses made-up object names (`dbo.Sim*`) and made-up column names
(`example/purchase-source-map.example.json`, `example/purchase-allowlist.example.txt`).

### 1. Regenerate with the candidate purchasing tables as roots

`--roots` replaces the default root list (the views of `--base-capture`), so list the
existing base views **and** the candidate purchasing objects. The foreign-key parents of
each root are pulled in by the closure.

```bash
D=scratch/mabna-capture-output
python3 deploy/mabna-sim/gen_schema.py $D/schema-capture-full.txt \
  --definitions $D/definitions-full.sql --base-capture $D/schema-capture.txt \
  --lookups $D/lookups.txt --row-counts $D/row-counts-full.txt \
  --roots <base views,candidate purchasing objects (comma-separated)>
python3 deploy/mabna-sim/check_order.py
```

### 2. Scenario: purchasing data in `generated/scenario.py` (gitignored)

Add the vendor, product, purchase invoice header, purchase return header and purchase line
tables to `TABLES` in `generated/scenario.py` and write their rows in `build_all(ctx)`
(see "Full capture" above for the `ctx` helpers). Cover these edge cases:

- vendor names with Arabic ي (U+064A) and ك (U+0643) next to Persian ی and ک;
- documents dated `1403/12/30` and `1404/01/01` (Jalali text, and numeric where the captured
  format has it; use `ctx.j2g` for any Gregorian column);
- a return dated in a later month than the invoice it returns;
- a cancelled document (set the cancelled column to its cancelled value);
- a line with no vendor and no product: set each nullable foreign-key column to an explicit
  `None`, so the row has no parent (a missing non-nullable key would be given a parent row);
- an empty month: no documents at all in one Jalali month.

Seedgen fills every other column. The scenario is the only place real column names appear,
which is why the file stays under `generated/`.

Then regenerate the seed:

```bash
python3 deploy/mabna-sim/gen_seed.py --capture $D/schema-capture-full.txt \
  --selection deploy/mabna-sim/generated/selection.json --row-counts $D/row-counts-full.txt \
  --lookups $D/lookups.txt --scenario deploy/mabna-sim/generated/scenario.py
```

### 3. Gitignored outputs for the sync and the flows

- `generated/purchase-source-map.json`: copy `example/purchase-source-map.example.json` and
  replace each made-up object and column name in the example with the captured candidate name.
  Keep every status `candidate`, `hostFiltered: false`, and the `discountBasis` the candidate
  map uses (contracts/source-map.md).
- `generated/allowlist.txt`: one `schema.object` per line for every object in that map. The
  sync refuses a map whose object is not on the allowlist (contracts/source-map.md, rule 2).
- `generated/src/purchasing-changes.sql`: hand-written simulator-only changes for Flow 6, run
  as `sa` in the simulator: add an invoice with lines, edit the line amount of one recent
  invoice, delete one recent return, and the old-document changes (spec 003 Phase 13, US2 AC5):
  set `IsCanceled = 1` on one invoice dated more than 60 days before the run, and delete one
  return dated more than 60 days before the run. The incremental sync must pick both up
  (quickstart Flow 6). The sync reads every header on each run, so a row's age does not matter.
  The generator does not write this file. It must never
  run against live Mabna.

Start the simulator with `docker compose -f deploy/docker-compose.mabna-sim.yml down -v && ... up -d`
after a regeneration, because `TotalSystem` is built only once.

### 4. Copy `generated/` into a worktree

Gitignored output is not in a fresh worktree. From the worktree root, copy the main checkout's
output (adjust the relative path to your layout; quickstart Flow 6 uses the same path):

```bash
cp -R ../../../zharfa/deploy/mabna-sim/generated/. deploy/mabna-sim/generated/
```

Only `generated/.gitkeep` is tracked; never `git add` anything else under `generated/`.

## Phase 2 scenario (spec 004)

Synthetic data for the vendor and purchasing reports (quickstart §0 and Flows P0–P10). It extends
the purchasing scenario above; every name is made up or comes from the gitignored candidate map.

Add to the scenario in `generated/scenario.py` (gitignored), on top of the Phase 1 tables:

- a drug group master (`SimDrugGroup`) with its key and name columns, plus a `SimDrugGroupID`
  column on the product table, so products point at groups;
- a `SimVendorCode` column on the vendor table;
- the quickstart §0 cases:
  - a vendor whose name is written with Arabic ي and ك, next to the Persian spelling;
  - a vendor name containing a ZWNJ (U+200C);
  - two vendors with the same normalized name and different codes;
  - a product without a category (`SimDrugGroupID` NULL);
  - a product whose category key is missing from the drug group master;
  - three years of documents (one Jalali month range per year, plus the current year);
  - a return dated in a later month than the invoice it returns;
  - a cancelled document;
  - more than 1,000 documents in one year, so the print limit (1,000 rows) is reached.

Regenerate with the candidate map and the allowlist from `example/` as in §3. Generator changes,
if any, must stay generic (no real names) in `gen_seed.py` and/or `seedgen.py`. The example map
(`example/purchase-source-map.example.json`) already carries the Phase 2 items with the made-up
names `SimVendorCode`, `SimDrugGroupID` and `dbo.SimDrugGroup` (`DrugGroupID`, `DrugGroupName`).

## Data-quality bad records (spec 005, US4)

`dq_bad_records.py` seeds synthetic bad records into the simulator so the Data quality page and the report notices can be
tested (contracts/sim-bad-records.md). It is generic: every table and column name is read from the purchase source map.

```bash
# 1. Generate (writes two scripts into the gitignored generated/dq folder; the Jalali date is a day of the test month)
python3 deploy/mabna-sim/dq_bad_records.py --map deploy/mabna-sim/generated/purchase-source-map.json --date 1405/07/15

# 2. Apply to the simulator only (sqlcmd -b stops at the first error; the password comes from the environment)
sqlcmd -S 127.0.0.1,14330 -U sa -P "$MABNA_SIM_SA_PASSWORD" -b -i deploy/mabna-sim/generated/dq/dq-apply.sql

# 3. Revert to the baseline (removes every seeded row and drops the bookkeeping table)
sqlcmd -S 127.0.0.1,14330 -U sa -P "$MABNA_SIM_SA_PASSWORD" -b -i deploy/mabna-sim/generated/dq/dq-revert.sql
```

The apply script ends with the manifest (`issue_type`, `seeded`). Expected seeded counts with the example map and every
item mapped: missing-values 4, duplicate-records 1, broken-relationships 3, inconsistent-product-ids 1, invalid-dates 2,
unexpected-quantities 2, inconsistent-amounts 3. The tracked example maps no `purchaseInvoice.docDiscount` column, so its
record 16 (document discount) is skipped and inconsistent-amounts shows 2; the skipped records are listed after the manifest.

Counts rise by exactly the seeded number after the next sync; the synced copy already has baseline issues from the
Phase 2 scenario, so compare with the baseline counts taken before applying (research R17). After the revert and the next
sync the page returns to the baseline.

The `generated/` folder is gitignored: the scripts and their output never enter the repository, and Zharfa itself never
runs them. Use the simulator only; the scripts are for the offline development database.
